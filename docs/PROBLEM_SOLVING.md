# Problem Solving

현재 기억과 보존 자료로 확인할 수 있는 범위만 기록합니다. 당시 최종 통합 소스가 없어
정확한 저수준 원인을 특정할 수 없는 항목은 관찰·조치·결과 중심으로 설명합니다.

## 시나리오 1 - 하드웨어 제약에 맞춘 게임 범위 조정

- **문제:** 초기에는 4인 플레이를 설계했지만 사용할 수 있는 포트와 게임 안정성에
  제약이 있었습니다.
- **판단:** 참가 인원 수를 유지하는 것보다 버튼 입력, 무작위 카드, 터치 판정과 점수라는
  핵심 게임 흐름을 안정적으로 완성하는 것이 중요했습니다.
- **조치:** 플레이어 대 컴퓨터 구조로 범위를 조정하고 컴퓨터 카드와 점수·승패 상태를
  소프트웨어 흐름에 포함했습니다.
- **결과:** 핵심 규칙을 유지하면서 실제 하드웨어에서 반복 가능한 최종 시연 구조를
  완성했습니다.

## 시나리오 2 - PIR 센서 위치와 판정 방식 개선

- **문제:** 초기 구상은 사용자가 특정 위치에 손을 유지하는지를 PIR 센서로 판단하려
  했지만, 실제 센서 성능과 동작 특성에 맞춘 조정이 필요했습니다.
- **판단:** 손의 정지 상태를 계속 확인하기보다, 조건을 만족하지 않은 상태에서
  터치센서로 손이 이동하는 행위를 감지하는 편이 실제 동작에 적합했습니다.
- **조치:** 손의 대기 위치와 터치센서 사이에 PIR 센서를 배치하도록 하드웨어 구조와
  판정 흐름을 함께 변경했습니다.
- **결과:** 잘못된 터치 시도를 감지해 감점하는 규칙을 실제 하드웨어 동작에 연결했습니다.

## 시나리오 3 - 마감 직전 전체 흐름 안정화

- **상황:** 실습실에서만 하드웨어 검증이 가능했고, 팀이 함께 작업할 수 있는 시간이
  발표 전날에 집중되어 있었습니다.
- **우선순위:** 새로운 기능을 늘리기보다 카드 출력, 버튼 입력, 점수 계산과 결과 출력의
  안정화를 우선했습니다.
- **조치:** 공동 작업일 전에도 단독으로 실습실을 찾아가 전체 구조를 분석하고 테스트했으며,
  발표 전날에는 팀원들과 오류를 공유하고 수정 결과를 반복 확인했습니다.
- **디버깅:** 잘못된 점수 계산, 버튼 입력 후 진행 정지와 무반응 문제를 재현하고,
  관련 상태 값과 분기 흐름을 하나씩 바꿔가며 결과를 비교했습니다.
- **완성도 개선:** 난이도, 게임 진행 순서와 규칙을 실제 플레이 흐름에 맞게 조정했습니다.
- **결과:** LCD 카드·점수 표시, 버튼 기반 진행과 스마트폰 터미널 결과 출력이 이어지는
  최종 동작을 확인했고 과제를 통과했습니다.
- **배운 점:** 담당 기능만 끝내는 것보다 전체 사용자 흐름을 이해하고 통합 단계의
  우선순위를 정하는 일이 완성도에 직접 영향을 준다는 점을 경험했습니다.

## 2026년 정적 검토에서 확인한 코드 항목

다음은 당시 기억이 아니라 현재 보존 코드에서 확인한 내용입니다.

### 초음파 센서 코드

- Echo 대기 루프에 timeout이 없어 센서 응답이 없으면 멈출 수 있음
- timer counter wraparound 처리가 없음
- timer update interrupt를 활성화하지만 보존 코드에 handler가 없음
- 거리 환산식과 출력 단위를 다시 검증해야 함

### 터치 센서 코드

- software delay가 최적화에 의해 제거될 가능성
- 출력 register 작성이 의도한 핀 외의 핀에도 영향을 줄 수 있음
- debounce와 edge detection이 없음

이 항목은 원래 과제의 실패를 뜻하지 않습니다. 전체 통합 최종본이 아니라 독립 실험
코드 일부만 남아 있으므로, 2026년 재구성 시 검증할 항목으로 사용합니다.
